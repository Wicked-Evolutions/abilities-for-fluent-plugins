## Defect

`fluent_abilities_schema_list_output($key,$obj)` / `_collection_output($key,$obj)`
/ `_item_output($obj)` (`includes/schemas.php`) treated their `$item_props`
argument as a property-name→sub-schema **map** and assigned it verbatim to a
JSON-Schema `properties` key. Callers pass a free-form schema **fragment**
`$obj = array('type'=>'object','additionalProperties'=>true)`. That declared a
phantom property literally named `type` whose schema was the **string**
`"object"`. Every FluentCRM row carries a real `type` column, so WP core
`rest_validate_value_from_schema()` recursed into a string and fatally
`TypeError: Cannot access offset of type string on string`
(`wp-includes/rest-api.php:2203`) inside `WP_Ability->validate_output()` — only
on **populated** responses (empty list → no per-item validation → no crash;
the cold-start signature, and why the P-J read-backs were "pending").

## 2. Fix

New shared resolver `fluent_abilities_item_schema_node($item_props)`:

```php
if ( is_array( $item_props ) && isset( $item_props['type'] ) && is_string( $item_props['type'] ) ) {
    return $item_props;            // schema fragment → use as item schema directly
}
$node = array( 'type' => 'object' );
if ( ! empty( $item_props ) ) { $node['properties'] = $item_props; }  // property map (unchanged)
return $node;
```

`schema_list_output` / `_collection_output` / `_item_output` now route through
it. Mechanical; zero behaviour change for legitimate property-map callers.
