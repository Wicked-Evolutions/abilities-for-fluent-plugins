# V1.1.3 Known Defects Ledger

> **Scope:** This document records existing defects in v1.1.3 abilities that the **Fluent Suite Registrar Bundle Sprint** (v2.0.0 release) has surfaced via per-plugin Ability Registrar Research. The defects below are **preserved as-is** in v2.0.0 per the Stable Ability Contracts principle (operators integrate against existing ability behavior; silent fixes break operator integrations). Each defect is tracked separately as a `v1.1.x-known-defect` GitHub issue against `main` for resolution in a future v1.1.x hotfix release.

> **Why this ledger exists:** Without it, dev chats working on the v2.0.0 sprint might misinterpret "Stable Ability Contracts = preserve as-is" as "everything existing is healthy." It is not. Some existing v1.1.3 abilities have known-broken behavior that the Stable Contracts gate intentionally preserves to avoid silently changing operator-visible behavior in a major release. The fix lane for these is v1.1.x hotfixes, not v2.0.0.

> **Sprint plan reference:** [`Plans/Alpha Release Gate/Fluent Suite Registrar Bundle Sprint 2026-05-13.md`](../../../00%20Influencentricity%20OS/Plans/Alpha%20Release%20Gate/Fluent%20Suite%20Registrar%20Bundle%20Sprint%202026-05-13.md) (vault path; canonical definition of the sprint and the broader Stable Contracts protocol).

---

## How to use this ledger

If you are a **dev chat** working on a Phase B per-plugin PR:

1. **Read the entries for your plugin before writing any code.** Some new abilities you add may interact with broken existing behavior — knowing the defect lets you avoid replicating the bug or building on top of it.
2. **Do NOT silently fix any v1.1.3 defect** in your PR. Even if the fix is one line, it changes operator-visible behavior. Stable Ability Contracts forbid this.
3. **If you find a NEW defect not listed here**, follow the dev-chat protocol below.
4. **Reference this ledger in your PR body** when relevant: "This new ability sits adjacent to v1.1.3 defect KD-N (preserved as-is per Stable Contracts; see ledger)."

If you are the **orchestrator** integrating a feature PR:

1. **Verify the dev chat has not silently fixed any ledger entry.** Phase B per-plugin source-diff (`git diff v1.1.3 -- includes/{plugin}/`) is the primary catch.
2. **If a NEW defect surfaces during Phase B**, file a `v1.1.x-known-defect` GitHub issue against `main` and add the defect to this ledger before approving the PR. The dispute about whether to preserve or fix is escalated to J.

## Defects by plugin

### FluentCart (`includes/cart/`)

#### KD-1 — `fluent-cart/create-product` writes wrong CPT

- **Symptom:** Products created via this ability have `post_type='fct_product'`. The actual FluentCart CPT is `'fluent-products'` (registered at vendor `app/CPT/FluentProducts.php:13`).
- **Live evidence:** Helena production has 3 broken zero-field product records resulting from prior use of this ability. Records are present in `wp_posts` with `post_type='fct_product'` but lack corresponding `fct_product_details` rows (the `'fct_product'` post type isn't joined by FluentCart's product loaders).
- **Source:** FluentCart Ability Registrar Research §1 + §6.1.
- **Disposition for v2.0.0:** **PRESERVE.** The broken behavior in `fluent-cart/create-product` ships unchanged. Any new product-creation ability added in this sprint uses the correct `'fluent-products'` CPT; the old ability stays as-is with a CHANGELOG note pointing operators to the new ability.
- **Hotfix tracking:** GitHub issue `v1.1.x-known-defect` (TBD) against `main` for separate v1.1.4 patch.

#### KD-2 — Eight schema/CPT drifts in existing 50 FluentCart abilities

- **Symptom:** FluentCart Ability Registrar Research §6.1 enumerated 8 distinct schema or CPT drifts across the existing 50 v1.1.3 FluentCart abilities. Full enumeration in the research file's §6.1 boundary observations table.
- **Source:** FluentCart Ability Registrar Research §6.1.
- **Disposition for v2.0.0:** **PRESERVE.** All 8 drifts ship unchanged in their existing v1.1.3 abilities. New ability surface designed in this sprint avoids the same patterns; correct schemas/CPTs used throughout the new abilities.
- **Hotfix tracking:** GitHub issue `v1.1.x-known-defect` (TBD); may be consolidated with KD-1 if scope warrants.

### FluentCommunity (`includes/community/`)

#### KD-3 — Always-false branch in CourseLesson namespace check

- **Symptom:** `community/abilities.php` lines 849, 898, 995, 1063, 1125, 2479 contain `if (class_exists('\\FluentCommunity\\App\\Models\\CourseLesson'))` checks. In FluentCommunity 2.4.01, **no such class exists** — the canonical namespace is `\FluentCommunity\Modules\Course\Model\CourseLesson` (under `Modules/`, not `App/Models/`). The branch always evaluates false. The fallback path (`Feed::where('type','lesson')`) is also unreachable because CourseLesson stores in `fcom_posts.type='course_lesson'`, not `'lesson'`.
- **Effect:** Net no observable issue (callers fall through both branches), but the CourseLesson-related code paths are dead code that mislead future readers.
- **Source:** FluentCommunity Ability Registrar Research v2.0 §3 + §6.
- **Disposition for v2.0.0:** **PRESERVE.** Dead branches stay. Any new community/course abilities added in this sprint use the correct `\FluentCommunity\Modules\Course\Model\CourseLesson` namespace and the `'course_lesson'` `fcom_posts.type` value.
- **Hotfix tracking:** GitHub issue `v1.1.x-known-defect` (TBD) against `main` for cleanup in a v1.1.4 patch.

### Fluent Bookings (`includes/booking/`)

#### KD-4 — Stale `$count = 22` in `abilities.php:1463`

- **Symptom:** `includes/booking/abilities.php:1463` contains the literal string `$count = 22` used in an `error_log` call. The actual registered ability count in that file is 21 (not 22). Off-by-one. Cosmetic only — affects only the `error_log` output, no operational impact.
- **Source:** Fluent Bookings Ability Registrar Research §6.1.
- **Disposition for v2.0.0:** **PRESERVE.** Cosmetic. No new abilities depend on this value.
- **Hotfix tracking:** GitHub issue `v1.1.x-known-defect` (TBD). Lowest priority; may be deferred indefinitely.

#### KD-5 — Status enum drift between read and write paths

- **Symptom:** Booking status enum drift between read-side and write-side abilities:
  - Read-side abilities use `no-show` (hyphen variant) — verified at `includes/booking/abilities.php:1258`.
  - Write-side abilities use `no_show` (underscore variant) — verified at `includes/booking/abilities.php:1368` (`update-booking-status`) and `:127` of `abilities-bookings.php` (`update-booking`).
- **Effect:** Operators mutating booking status MUST use the underscore variant `no_show`. Operators reading booking status receive the hyphen variant `no-show`. Cross-ability data flow (read → write) requires manual translation.
- **Source:** Fluent Bookings Ability Registrar Research §6.2.
- **Disposition for v2.0.0:** **PRESERVE the mismatch in the v1.1.3 abilities** (operators may have integrated against this exact translation step). Document the mismatch in v2.0.0 release notes. Any new write-side abilities added in this sprint use the vendor-canonical form (verify against vendor source before settling on the variant) AND document the legacy mismatch in PR body.
- **Hotfix tracking:** GitHub issue `v1.1.x-known-defect` (TBD). Resolution in v1.1.4 may unify to one variant + add deprecation notice to the legacy form.

### Fluent Boards (`includes/boards/`)

#### KD-6 — Cross-board `move-task` is destructive (intentional, undocumented)

- **Symptom:** The `fluent-boards/move-task` ability, when moving a task between boards (not just between stages within a board), erases board-specific relations: assignees, labels, watchers, custom fields, comments, and activity log entries. This is **intentional cleanup** (per vendor design — the moved task no longer belongs to its prior board's relations) but is undocumented in the ability description.
- **Effect:** Operators using `move-task` for cross-board moves lose data they may not expect to lose. Operators using it for within-board stage moves are unaffected.
- **Source:** Fluent Boards Ability Registrar Research §6.5.
- **Disposition for v2.0.0:** **PRESERVE behavior.** Document the destructive nature in the v2.0.0 release notes + in PR body for any new task-move-related ability. **Not a defect to FIX** — it's a documentation gap. Any new ability that wraps cross-board task moves SHOULD include explicit destructive-warning language in its description.
- **Hotfix tracking:** GitHub issue `v1.1.x-known-defect` (TBD) for description/documentation cleanup in v1.1.4. Behavior unchanged.

#### KD-7 — `Board::boot` global scope excludes sales-pipeline boards

- **Symptom:** `Board::boot` at vendor `Models/Board.php:42-43` adds a global Eloquent scope: `where('type', '=', 'to-do')->orWhere('type', '=', 'roadmap')`. Sales-pipeline boards (`type='sales-pipeline'`) are silently excluded from any Eloquent-based query through the `Board` model. The existing module's `abilities.php:45, 113, 159` works around this by using raw `wpFluent()->table('fbs_boards')` queries (which bypass the global scope).
- **Effect:** New abilities that use the Eloquent `Board` model will silently exclude sales-pipeline boards. New abilities using raw `wpFluent` queries will include them. Inconsistency risk between abilities depending on which approach the dev chat picks.
- **Source:** Fluent Boards Ability Registrar Research §6.
- **Disposition for v2.0.0:** **NOT A DEFECT — STRUCTURAL QUIRK.** Document for the Boards dev chat: choose ONE approach per new ability (Eloquent for all-non-pipeline coverage; raw queries for full coverage including pipelines). Be consistent within a related cluster of abilities. Document the choice in the ability description.
- **Hotfix tracking:** Not a hotfix candidate — vendor-side design choice; can't be fixed without forking the Board model.

## Dev chat protocol when surfacing a NEW defect during Phase B

1. **STOP** work on any ability that depends on the defective behavior. Do not write a workaround. Do not try to fix it. Do not "make it work" by ignoring it.
2. **Report to orchestrator** with:
   - Source citation (file:line)
   - Reproduction steps
   - Live evidence (response payload showing the defect)
   - Affected abilities (which v1.1.3 abilities depend on the broken behavior; which proposed new abilities are blocked)
3. **Wait for orchestrator disposition.** Orchestrator decides:
   - **Preserve** (most common) — defect added to this ledger + filed as `v1.1.x-known-defect` issue against `main`. Dev chat resumes with disposition guidance.
   - **Expand sprint scope** (rare; J-authorized only) — defect upgraded to a v2.0.0 in-scope fix. Sprint plan amendment required per `feedback_no_mid_sprint_scope_expansion`.
4. **Resume work** once disposition is clear. Reference the new ledger entry in your PR body.

## Ledger maintenance

This ledger is the canonical reference for v1.1.3 known defects throughout the Fluent Suite Registrar Bundle sprint. Updates happen at orchestrator-only:

- **Add a new entry** when a dev chat surfaces a NEW defect during Phase B (per protocol above).
- **Update an entry's disposition** if J authorizes a scope-expansion to fix a defect in v2.0.0 (rare).
- **Mark an entry resolved** when the v1.1.x hotfix shipping the fix is released. Strikethrough the entry but keep it for audit.

After v2.0.0 ships, this ledger continues to track open `v1.1.x-known-defect` GitHub issues until they're resolved in v1.1.x hotfix releases or formally accepted as won't-fix.
