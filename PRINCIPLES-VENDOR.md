# FLUENT SUITE PRINCIPLES — Vendor Compatibility Contract

> **Status:** v1.0 ratified 2026-05-15 by J. Binding operating contract for `abilities-for-fluent-plugins`. Co-authored by Claude Code orchestrator + GPT 5.5 across four turns.
>
> **Binding scope:** `abilities-for-fluent-plugins`. Other suite repos (`abilities-mcp`, `abilities-mcp-adapter`, `abilities-for-ai`) are governed by the companion `PRINCIPLES.md` (Official WordPress Compatibility Contract). The two contracts compose: a Fluent-plugin ability must satisfy both. This contract is stricter at the vendor layer; nothing here overrides the WordPress platform contract.

---

## North Star

The vendor dev docs are the vendor-native contract. Our `abilities-for-fluent-plugins` registrars are product layers around the vendor's existing API surface — not bypass wrappers around its storage.

| Layer | What it does | What it does NOT do |
|---|---|---|
| Vendor (FluentCommunity, FluentCRM, FluentCart, FluentBoards, Fluent Forms, Fluent Bookings, FluentPlayer) | Defines the canonical REST endpoints, service classes, models, field names, vendor-published abilities | We do not redefine these |
| `abilities-for-fluent-plugins` registrars | Expose vendor operations as `wp_register_ability()` callbacks that route through the vendor's documented surface | Skip the vendor's documented surface to write to storage directly |
| Adapter / Bridge | Project, scope, redact (per the platform `PRINCIPLES.md`) | Compensate for divergence introduced at the registrar layer |

A single sentence rule: **route through the vendor's documented surface, not around it.**

| Source | Role | Binding? |

| Vendor plugin source (the actual installed `fluentcrm/`, `fluent-community/`, etc.) | Behavior authority for the version under test; resolves cases where dev docs are silent, outdated, or in conflict | **Yes** |
| Companion `PRINCIPLES.md` (Official WordPress Compatibility Contract) | Platform contract | **Yes, composes above this doc** |
| WordPress core Abilities API | Platform contract | **Yes** (per the WP Compatibility Contract) |
| This document | Vendor-product contract for `abilities-for-fluent-plugins` | **Yes, for that repo** |

**Operating sentence:**

> We follow the vendor's documented surface as the vendor-native contract, pinned to the vendor version installed in the probe environment. Where vendor dev docs and vendor source disagree, vendor source wins for behavior and dev docs win for description. Disagreements are filed back with the vendor where appropriate. Our schemas describe the vendor's surface — not a re-interpretation of it.

> **Caution on principle-checking:** When dev docs are silent or wrong, the installed vendor source is the behavior authority. A principle check that uses only the dev doc as evidence is incomplete; the registrar must verify against the installed source at the vendor version it's pinned to.

## Principles (binding for `abilities-for-fluent-plugins`)

### V1. Vendor Dev Docs Are The Vendor Contract

Every Fluent-plugin ability that maps to a documented vendor REST endpoint, vendor service-class method, vendor public API, or vendor-published ability uses that documented surface as the source of truth for:

- Field names (request and response)
- Required vs optional parameters
- Required vs optional response fields
- Endpoint or ability identity (which vendor operation we're wrapping)
- Permission expectations stated in the dev docs

Schemas do not invent vendor field names, do not declare required what the vendor says is optional, do not omit a field the vendor's documented response actually includes.

**Dev docs bind through the vendor version they describe.** The installed vendor source is the behavior authority for the version under test; dev docs provide the intended public contract and must be reconciled when they disagree.

### V2. Canonical Vendor Namespace

When the vendor maintains parallel namespace trees (e.g., `\FluentCommunity\App\Models\Space` vs `\FluentCommunity\Modules\Course\Model\Course`, or `\FluentCrm\App\Models\Sequence` vs `\FluentCampaign\App\Models\Sequence`), ability callbacks use the namespace the vendor designates as canonical for the operation.

A vendor namespace is **canonical** when:

- The vendor's dev docs reference it (directly or via the documented REST handler implementation), OR
- The vendor's REST controller for the operation calls into it, OR
- The vendor's deprecation/migration notes designate it as the surviving namespace.

The `fluent-community/create-course` drift (the founding example in the Drift Examples table below) is the prototypical violation: write-side used legacy `App\Models\Space`; read/enrollment-side correctly used `Modules\Course\Model\Course`; cross-table inconsistency produced 7 cascade failures in the v1.4.0 cold-start re-test.

### V3. Documented Vendor Operation Before Direct Storage, With Read-Back Proof

When the vendor exposes a documented operation for the action, ability callbacks use that operation in this priority order:

1. Documented vendor REST endpoint / controller path.
2. Vendor public service class or public helper used by that endpoint.
3. Canonical vendor model (per V2) **only when** no documented endpoint/service exists.
4. Raw table write **only when** the vendor source itself treats the table operation as the public operation AND the ability registrar carries explicit rationale in a code comment (not just the PR description).

The service layer fires the vendor's hooks, validates inputs against vendor invariants, dispatches events, updates caches, and triggers webhooks. Direct model or storage writes skip all of that and produce orphaned state that downstream vendor code cannot reconcile.

**Read-back verification is required for every write ability.** Every `create-*` / `update-*` / `delete-*` ability identifies a vendor-facing read path that proves the write landed in the same surface downstream operations expect. Examples:

- `create-course` must be visible to `list-courses` / `get-course`, not just `list-spaces`.
- `create-product` must read back price and timestamps through product/pricing reads.
- `send-message` must return the same persisted message ID that `list-messages` sees.

**Direct-storage writes** (priority 4) require three receipts before merge:

1. No documented REST/service/public helper found (named in the registrar comment).
2. Canonical namespace verified (per V2).
3. Post-write read-back verifies the vendor-facing API can see the record.

### V4. Vendor-Native Field Names And Schema Descriptions

Extends Principle 4 of the companion `PRINCIPLES.md` (Official WordPress Compatibility Contract) with a vendor-side clarification:

- **Vendor-native** means what the vendor's REST endpoint or vendor-published ability accepts per the vendor's dev docs.
- Where the vendor uses non-obvious names (`feed_id` vs `post_id` for the same entity in different contexts; `space_id` vs `course_id` when courses are spaces with `type=course` in some implementations), the `input_schema` description text names the vendor-doc context in plain language. Example: `'description' => 'Course ID from the vendor /courses/{id} API. Do not pass a space ID unless it is returned by the course endpoint.'`
- **No renaming for AI-consistency across abilities** — the existing platform Principle 4 absolute holds. We clarify in descriptions; we do not rename.

### V5. Responses Cross The Ability Boundary As Vendor Data, Not Framework Internals

`output_schema` declares the shape the vendor actually returns per the vendor's dev docs, including documented empty-case shapes.

**Framework objects do not cross the ability boundary.** Eloquent models, FluentForm Collection objects, Laravel paginators, Request objects, WPDB result resources, and vendor service instances are normalized to plain arrays/scalars before return.

For shape variations between dev docs and installed runtime:

- **Empty-state normalization (default).** If vendor docs say "array" and installed vendor source returns `null` only for the empty case, the ability normalizes `null → []` at the boundary, with a code comment naming the vendor source line. This preserves the documented empty-collection contract; it is not field-renaming or AI-cosmetic normalization.
- **Documented alternatives (union-declare).** If vendor docs and vendor runtime genuinely support two meaningful shapes for the same operation, `output_schema` declares the union.
- **Framework internals (boundary bug).** If the runtime returns framework internals (`onEachSide:3` paginator state, Eloquent traits like `incrementing` / `preventsLazyLoading`, Collection objects), this is not a legitimate alternative output shape. Normalize to the vendor data shape. Do not union-declare framework leakage.

### V6. Registrar Carries Dev-Doc Pointer

Every ability registrar that wraps a documented vendor surface carries a PHP comment with:

- Vendor doc URL.
- Endpoint/method, service class, or vendor-published ability name.
- Verified vendor plugin version or dev-doc snapshot date.

Schema descriptions include the vendor-doc context (URL or plain-language reference) **selectively** — for ambiguous vendor naming (`id` vs `course_id`, `space_id`, `feed_id`), destructive/full-replace behavior (V8), composite workflows, or vendor precondition caveats. Full dev-doc URLs are not added to every description; that bloats discovery and teaches the AI to read external docs in normal operation.

For ambiguous fields, prefer plain-language vendor context in the description over a bare URL:

> `id`: Course ID from the vendor `/courses/{id}` API. Do not pass a space ID unless it is returned by the course endpoint.

### V7. Ability Input Is Whitelisted Before Persistence

Callbacks only persist fields declared in `input_schema` or explicitly derived from them. They must not pass raw `$input` wholesale into vendor storage when the input may include adapter/client envelope fields.

Before any create/update call that persists arbitrary arrays, the registrar constructs a vendor payload from an allowlist of schema-declared fields. Unknown keys are ignored or rejected; they are never stored.

This is the contract guard against the `create-webhook` security-adjacent incident where MCP transport envelope fields (`method`, `params`, `jsonrpc`, `id`, including a claude-code tool-use ID) were persisted into the webhook record.

### V8. Full-Set Replacement Is Destructive Unless Proven Otherwise

Any ability that replaces a whole vendor set from an array input must declare that behavior in **both**:

- Schema description (plain-language warning naming the replacement semantics), AND
- `annotations` with `destructive: true`.

Empty array (`[]`) is not treated as harmless by default. If `[]` means "clear all," the ability is destructive AND its field description names the semantics in plain language: *"Empty array clears all entries; this is a full replacement, not a delta. To remove a subset, use [sibling-slug]."*

This is the contract-level guard for the `fluent-crm/update-contact-custom-fields` stop-condition event (8 production custom field definitions wiped on `helenawillow` during Phase 2 of the v1.4.0 cold-start re-test). Annotation alone is not enough; description alone is not enough; both are required because different AI clients read different surfaces.

### V9. Returned Identifiers Must Round-Trip

If a write returns `id`, `message_id`, `activity_id`, `course_id`, etc., that value must be the persisted vendor primary identifier usable by the corresponding read/update/delete abilities.

A returned identifier is a public contract. It must round-trip through the next ability in the lifecycle. Examples from the v1.4.0 re-test:

- `fluent-messaging/send-message` returned `message_id: 1` while the stored message was `189` (the ID `list-messages` sees).
- `fluent-bookings/add-booking-note` returned `activity_id: 1` while the actual stored ID was ≥3291.

Both are V9 violations: the caller relying on the returned ID would reference the wrong record.

### V10. Vendor Preconditions Become Typed Errors, Not PHP Fatals

Missing vendor module, missing table, absent class, disabled Pro feature, or wrong controller/request signature must resolve to a typed `WP_Error`, not a PHP TypeError or connection-closing fatal.

This does not mean the operation must work when the vendor module is absent. It means absence is reported cleanly. Examples from the re-test:

- Community: `Utility helper not available`, `NotificationPref model not available`.
- Bookings: `TimeSlotService` class mismatch in constructor.
- CRM: validator/request TypeErrors in `create-pro-manager`, `list-funnel-templates`, `sync-subscribers-segments`.
- Community: `update-privacy-settings` PHP TypeError (handler expects Request, registrar passes array).

**Vendor state may block an ability; it must not crash the ability process.**

### V11. Dev-Doc Cross-Check Is Definition-Of-Done

A Fluent-plugin ability is **done** only when:

- The registrar maps to a documented vendor surface (V1) and uses the canonical namespace (V2) and routes through the documented vendor operation (V3) with read-back verification.
- Input schema field names and required/optional flags match the dev docs (V4).
- Output schema reflects the documented vendor response shape and does not leak framework internals (V5).
- The registrar links the dev-doc URL in a PHP comment, plus selective AI-visible context where ambiguous (V6).

**Reviewer obligations at PR time** — applied only where the PR touches them; PR evidence states "applicable" or "not applicable" for each, with a one-line reason:

- **(a) Input whitelist** — write/update callbacks construct vendor payload from declared schema fields; no wholesale `$input` pass-through. (V7)
- **(b) Full-replace semantics** — abilities accepting array params with replace-semantics carry `destructive: true` annotation AND plain-language description warning. (V8)
- **(c) Returned ID round-trip** — write ability's returned identifier matches what the corresponding read ability sees; evidence in PR test fixture or tester verification. (V9)
- **(d) Typed error paths** — vendor precondition paths return `WP_Error`, verified by test of the absent-vendor case where applicable. (V10)
- **(e) Framework-object boundary** — output normalized to plain arrays/scalars; no Eloquent / Collection / paginator state in response. (V5)

Reviewers don't run all five for every PR; they run the ones relevant to what the PR touches. PR evidence states "applicable" or "not applicable" for each obligation, with a one-line reason.

**Vendor releases that update dev docs or install a new vendor version in the probe environment trigger a re-check pass** on affected abilities. The re-check is a PR-sized chore, not a sprint. CI does not scrape live dev docs; vendor compatibility is rechecked on vendor-version change or on a human-noticed vendor changelog/dev-doc change that touches endpoints/models/schemas.

### V12. Context Abilities Guide Composition But Do Not Excuse Drift

Plugin context abilities (e.g., FluentCRM's native `get-crm-context`) may expose valid enums, IDs, vendor preconditions, safety hints, and recommended workflows. They help the AI choose and sequence abilities.

**Context abilities cannot relax or compensate for any violation of V1-V11.** A context ability can help the AI call `create-course` safely; it cannot make a legacy-space write acceptable.

When plugin context abilities are added, they slot into the existing layered architecture without introducing a parallel layer:

```
knowledge/boot              → operator/site/session/agent context
fluent-{plugin}/get-context → plugin-specific operating map
skill / protocol docs       → task-specific procedure
granular abilities          → execution
```

The design of context abilities is out of scope for this contract — it is separate post-v1.4.0 exploration. This principle is a guardrail only.

## Decision Heuristic

Before merging any new or modified Fluent-plugin ability, ask in order:

1. Which vendor dev-doc endpoint, service class, vendor-published ability, or public function does this ability map to?
2. Have I read that dev-doc page (or vendor source) in its current state at the installed vendor version?
3. Does the `input_schema` field set + required/optional flags match the dev docs?
4. Does the callback route through the canonical vendor namespace + documented operation (per V3's priority hierarchy)?
5. Does the `output_schema` reflect the documented response shape, with no framework internals?
6. For writes: what's the read-back call that proves the write landed in the vendor-facing surface?
7. For writes accepting arrays: does `[]` mean "clear all"? If yes, is V8 satisfied (destructive annotation + description warning)?
8. Is the returned identifier the vendor primary identifier downstream lifecycle calls will use?
9. Are vendor preconditions (absent class/table/module) handled as `WP_Error`, not PHP fatals?
10. Is the dev-doc URL captured in the registrar PHP comment?

If any answer is "no" or "unclear," pause and reconcile before merging.

## Vendor-Map Coverage Artifact

`docs/vendor-map/fluent-*.json` files in this repo carry one entry per ability:

```json
{
  "ability": "fluent-community/create-course",
  "vendor": "fluent-community",
  "vendor_version_checked": "2.1.02",
  "authority": "rest_endpoint",
  "method": "POST",
  "endpoint": "/fluent-community/v2/courses",
  "doc": "Products/Dev Docs/Fluent Dev Docs/FluentCommunity/REFERENCE Courses API FluentCommunity.md",
  "canonical_handler": "vendor REST courses controller",
  "direct_storage": false,
  "read_back": {
    "ability": "fluent-community/get-course",
    "field": "id"
  },
  "notes": "Create must be visible through list-courses/get-course after write."
}
```

CI checks:

- Every `fluent-*` ability has a vendor-map row or an explicit exception.
- Every row has `authority` / `doc` / `vendor_version_checked`.
- `direct_storage: true` rows carry a rationale.
- Write/delete rows declare a `read_back` path.

This is the vendor equivalent of the WP contract's `ScopeCoverageDriftTest` (Principle 9 in the platform contract): not a perfect proof, but a drift detector. It would have made `create-course` suspicious before live testing.

## Drift Examples — what we don't do

Living record — appended as new violations are caught and corrected.

| Proposal / pattern | Violated | Why it drifted |
|---|---|---|
| `fluent-community/create-course` writing to `\FluentCommunity\App\Models\Space` with `type='course'` flag instead of `\FluentCommunity\Modules\Course\Model\Course` | V1, V2, V3 | Used the legacy namespace + bypassed the vendor's courses REST service. Downstream course abilities correctly use canonical namespace, can't find what create-course wrote. 7 cascade failures in v1.4.0 cold-start re-test. |
| `fluent-crm/create-webhook` persisting MCP transport envelope (`method`, `params`, `jsonrpc`, `id`, claude-code `toolUseId`) into stored webhook record | V7 | Handler passed wholesale `$input` to vendor storage; no schema-declared-field allowlist construction step before persistence. Security-adjacent. |
| `fluent-crm/update-contact-custom-fields` with `{"fields": []}` wiping 8 production custom field definitions on `helenawillow` | V8 | Schema declared `fields` as optional array with no encoding of empty-array semantic. Handler treats `fields: []` as full-replace. Ability had `permission: write`, no `destructive: true` annotation, no description warning. Both V8 receipts missing. Stop-condition event during Phase 2 of cold-start re-test. |
| `fluent-messaging/send-message` returning `message_id: 1` while persisted ID was `189` | V9 | Handler returned a positional/relative value, not the vendor primary identifier. Caller using the returned id references wrong record. |
| `fluent-bookings/create-event` PHP TypeError (`reset()` on null) crashing the ability process | V10 | Vendor/source precondition hit an uninitialized `team_members` value (non-simple calendars) and called `reset()` without an array guard. Should resolve to `WP_Error`, not crash. |
| Eloquent model internal traits (`incrementing`, `preventsLazyLoading`, `wasRecentlyCreated`, etc.) and Laravel paginator state (`onEachSide:3`) leaking into `structuredContent` of ~20 CRM read responses | V5 | Vendor returned the model/paginator object directly; ability returned it without `->toArray()` projection or output normalization. Framework internals crossing the ability boundary. |
| `output_schema` declaring a key as `array` while the vendor returns a paginator object / `{data,total}` wrapper / id-keyed map / `(object)` cast (~32 reads across CRM/Cart/Bookings, P-H) | V5, V4 | Schema asserted a shape the vendor never emits → the ability's own output validator rejected a valid vendor response. Fixed P4b: paginator/wrapper-aware boundary normalize per-slug; union-declare where the vendor genuinely returns an object. | 
| `fluent-forms/create-form` returning the operator's input verbatim while the vendor persisted `My New Form (#N)` / `published` / `form_fields:null` (F-FORMS-01) | V3, V9 | Callback fabricated its return from `$input` instead of reading back the persisted record; routed through the vendor's template-seeded `FormService::store()` which ignores flat title/status. Fixed P3c: vendor-model write + read-back return. |
| `fluent-crm/get-template` returning a blank default placeholder with HTTP 200 when `Template::find()` misses (no 404) | V3 | Vendor route silently fabricates an empty template on a not-found id; the ability surfaced it as success. Caller cannot distinguish "not found" from a real empty template. Fixed P4b (Add.15(b)): id guard + placeholder-sentinel → typed `not_found`. |
| `fluent-crm/get-report-top-campaigns` proxying `GET /reports/top-campaigns` — a route that does not exist in the installed vendor route table (404) | V1, V3 | Registrar invented a vendor surface; no `top-campaigns` route exists (closest: `reports/campaigns-list`). Separable defect — bounced to reviewer, not auto-repointed. | 
| Prescribing `oneOf` ("exactly one of `attachment_id`/`image_url`; both rejected") for 5 FluentBoards upload abilities **without verifying the installed handler** — which uses `if($attachment_id) elseif($url)` precedence (both accepted, only neither rejected) | V11, P4 | A fix premise (even a dispatched one) asserted a handler contract the installed source contradicts; applying `oneOf` would have *false-rejected handler-valid input*. Corrected to `anyOf` (at-least-one) against installed-source truth. **Caution: principle-checking must verify installed source, not a prescribed premise.** |
| Registrar `Source: <Class>::<method>` citations naming vendor methods that do not exist in the installed source (pervasive across CRM/Cart/Forms/Community/Bookings) | V4 | Descriptions cited aspirational/stale handler names; the real handler resolves via the vendor route table. Documentation-only drift (no behavior impact) — corrected in the P5 editorial pass on touched slugs; remainder a tracked V4 follow-up. |
| `fluent-crm/set-global-email-style` forwarding `style` while vendor `setGlobalStyle` reads `config` — schema-valid input silently discarded, success returned | V3 | Handler reads a different key than the ability forwards; the operator's style is dropped with a misleading success (P-L shape). Reclassified out of the P5 editorial pass (executable behavior, not naming); escalated. |

Caught during the v1.4.0 cold-start re-test (2026-05-14 — 2026-05-16). Future drifts get caught at PR or sprint-plan review using the same lens.

## One closing note

The purpose of this contract is not purity. It is preventing drift: wrong table, wrong namespace, wrong payload, wrong returned ID, wrong shape, wrong precondition handling. Twelve principles is more than usual for a contract document, but each principle maps to a verified failure class from the v1.4.0 cold-start re-test. Nothing here is ornamental. The contract is slightly more explicit than elegant because this is a dev/reviewer guardrail, not marketing copy.

Do not turn this into a commandment that every ability must use vendor REST at runtime. Some vendor REST paths may be awkward, internal, incomplete, or less stable than a public service/model. The binding standard is "documented vendor operation and canonical namespace with read-back proof," not "REST at all costs."
